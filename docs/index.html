M17export: Field-to-Hub M17 Reflectors

A containerized fork of the mrefd M17 reflector. Small field nodes run on local support networks, advertise themselves over mDNS, and relay into hub instances of the same software that connect them to the wider M17 network.

Repository: github.com/greggwon/M17export Reflector fork: github.com/greggwon/mrefd Upstream: n7tae/mrefd

1Overview

M17 is an open digital-voice protocol for amateur radio. Unlike DMR, D-STAR, and YSF, it uses no patent-encumbered codec. Radios and hotspots connect to reflectors, which are servers that rebroadcast each transmission to everyone on the same module (a lettered room, A–Z). Reflectors can be interlinked so a module on one reflector is shared with a module on another.

This project is made of three pieces that work together:

  1. A fork of mrefd (the reference M17 reflector by N7TAE), maintained at greggwon/mrefd. The fork adds an authenticated TLS interlink, so a reflector with no fixed IP address (a field node) can relay into another instance of itself (a hub) that has a stable public address and wider connectivity.
  2. Container packaging that reduces deploying a reflector to filling in one environment file and running one command. It builds for arm64, armv7, and amd64, so the same deployment runs on a Raspberry Pi in a go-kit or on a cloud VPS.
  3. m17-advertise, a small Go program that announces a reflector on the local network over Bonjour / mDNS. M17 apps on the same network (such as MSeven) find it automatically, with no addresses to type.

The intended deployment is a hub-and-spoke network. Hubs are long-lived, publicly reachable reflectors. Field nodes come up wherever they are needed: an EOC, a shelter, a Field Day site, a club meeting. Each field node serves local users over the site LAN, finds its hub on its own, and carries traffic through it to the rest of the M17 world.

2Architecture

Node roles

Every node runs the same container image. Its role depends only on configuration.

Hub node ("home")

  • Always on, with a stable public IPv4 and/or IPv6 address (VPS, club server, home Pi with port forwarding).
  • Runs a TLS listener on TCP 17000 (the same number as M17 UDP) and accepts field nodes whose certificates it has registered.
  • Interlinked with other reflectors, gateways and hubs using static addresses (UDP) or TLS.
  • Holds server.crt/server.key, plus one peers/<CALLSIGN>.pub.pem for each operator whose nodes may connect.

Field node

  • Portable: Raspberry Pi, NUC, or laptop. Its IP changes from site to site, and it is often behind CGNAT, LTE, Starlink, or hotel Wi-Fi.
  • Dials out to the hub over TLS, so no inbound ports are needed from the internet.
  • Announces itself on the site LAN with mDNS, so local apps find it without configuration.
  • Holds its operator's client.crt/client.key (one pair per operator, shared by all their nodes) and a pinned copy of each hub's cert (hubs/M17-HUB.crt).

A node can also stand alone: a plain public reflector, or an isolated local reflector with no uplink at all. An isolated field node is still useful. During an outage it gives everyone on the site network a shared voice channel, and mDNS still lets them find it.

Glossary

Reflector
A server that rebroadcasts M17 voice and data among connected clients. Identified by a callsign of the form M17-XYZ.
Module
A lettered channel (A–Z) on a reflector. Clients connect to one module. Each enabled module uses its own processing thread.
Interlink
A peering between two reflectors that shares one or more modules. Both sides must configure it.
Ham-DHT
A distributed hash table (built on OpenDHT) where reflectors publish their addresses and metadata, so peers can find each other by callsign instead of by IP. Field nodes run without it: they are reached only through their hub and are never published. Whether hubs publish on Ham-DHT is not settled yet; the image can be built either way.
dvref.com
The community directory of M17 reflectors and interlink gateways.
mDNS / DNS-SD / Bonjour
Multicast DNS (RFC 6762) and DNS-Based Service Discovery (RFC 6763). Devices on one local network announce and discover services without a DNS server. Bonjour is Apple's name for it; Avahi is the Linux implementation.
MSeven
An Apple-native (iOS/macOS) M17 client. It reads the _m17._udp advertisements and the sites.json reflector directory.
Identity (TLS)
A field node's name at the hub, CALLSIGN-MODULE, for example W5ABC-B. The callsign always comes from the operator's certificate; the node only chooses the module. One operator certificate serves all of that operator's nodes, one node per module.

  • An mrefd admin socket. It was never built and is no longer needed: removing an operator's key on the hub disconnects their nodes immediately.

There are two ways to deploy, and each has its own compose file:

  • Repository root is the developer path. It builds images from the submodule source, adds the optional web dashboard, and provides the make targets. Its compose file also mounts config/tls/.

5Prerequisites

Deployment host

  • Linux: Raspberry Pi OS 64-bit, Debian 12, Ubuntu 22.04 or newer, or any distribution with a current Docker Engine. Host networking and LAN mDNS work only on a Linux kernel. See Networking for macOS caveats.
  • Hardware: a Raspberry Pi 3 or newer is enough for a field node with a few modules. A hub with many interlinks is better on a Pi 4/5 or a small VPS.
  • Docker Engine with Compose v2:
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER"
newgrp docker            # or log out and back in
sudo apt-get install -y git make

Additional tools for building from source

  • Docker buildx (included in current Docker Engine and Docker Desktop). QEMU emulation for cross-arch builds is installed automatically on first use.
  • Go 1.25 or newer, only if you want to run m17-advertise outside the container (for example, on a Mac). On macOS: brew install go.
  • openssl 1.1.1 or newer, for the TLS key scripts. Linux has it. On macOS the built-in LibreSSL can't make Ed25519 keys; brew install openssl@3 and the scripts find it on their own. Or run the scripts from the image (see TLS setup).

Before you go on the air

  • Choose a reflector callsign M17-XYZ (three characters, A–Z or 0–9) that is not already listed at dvref.com. A field node that stays private behind its hub still needs a callsign that is unique inside your own network.
  • Decide which modules you will use, and give each one a purpose. For example: A = international, B = regional, C = local net, D = ARES tactical.

6Getting started

Path A: deploy a prebuilt image (recommended)

The published image ghcr.io/greggwon/mrefd:latest is public and covers linux/amd64, linux/arm64, linux/arm/v7, and linux/386. Docker pulls the right variant automatically, including for a Pi 3 or Zero 2W running 32-bit Raspberry Pi OS. The 64-bit OS is still the better choice on hardware that supports it.

  1. Get the deployment bundle. 
    git clone https://github.com/greggwon/M17export.git
cd M17export/deploy
    You can also copy only the deploy/ directory to the target machine.
  2. Create your configuration. 
    cp mrefd.env.example mrefd.env
nano mrefd.env
    Only two values are required: 
    MREFD_CALLSIGN=M17-XYZ
MREFD_MODULES=B,C,D
    Also fill in MREFD_COUNTRY, MREFD_EMAIL and MREFD_DASHBOARD_URL. They go into the mDNS record, and they become required if you turn Ham-DHT on. If this reflector should be easy to recognize on a local network, also set MREFD_ADVERTISE_NAME (see mDNS discovery).
  3. Check the list files. config/mrefd.whitelist, config/mrefd.blacklist, and config/mrefd.interlink must exist as files. If they are missing, Docker creates directories in their place and mrefd fails to start. 
    ls -l config/
touch config/mrefd.whitelist config/mrefd.blacklist config/mrefd.interlink
  4. Start the reflector. 
    docker compose up -d
docker compose logs -f
  5. Open the firewall for the ports in Ports: UDP 17000 for clients and UDP interlinks, and TCP 17000 on hubs that accept TLS field nodes.

Path B: build from source

  1. Clone with submodules. 
    git clone --recurse-submodules https://github.com/greggwon/M17export.git
cd M17export
# if you already cloned without them:
git submodule update --init --recursive
  2. Run the setup wizard. It asks for callsign, modules, country, email, dashboard URL, sponsor, and ports. It then writes .env from .env.example, keeping all the comments, and seeds config/ with the upstream list-file templates. 
    make init
  3. Build the images for the machine you are on. This builds both the reflector and the dashboard image. 
    make build-local
    On a Raspberry Pi 3 the first build takes a while, because the C++ build stage compiles mrefd from source.
  4. Start the services. 
    make up               # reflector only (headless)
make up-dashboard     # reflector + web dashboard on http://<host>:8080/
make logs-mrefd       # follow reflector logs

7Configuration reference

All settings are environment variables. Put them in .env (source build) or deploy/mrefd.env (prebuilt). Each time the container starts, docker/mrefd/entrypoint.sh checks the required values, renders /etc/mrefd/mrefd.cfg, and refuses to start if a value is a placeholder or malformed. After changing a value, apply it with make restart or docker compose up -d.

8Networking and firewall

Host networking (the default)

The mrefd service uses network_mode: host. On Linux this gives you four things:

  • mrefd binds directly to the host's real IPv4 and IPv6 addresses, with no NAT in between.
  • IPv6 works natively. This matters for hosts behind residential CGNAT that have no usable inbound IPv4.
  • The advertiser's mDNS multicast reaches the physical LAN directly. This is required for local discovery.

Bridge mode

Some environments forbid host networking, and Docker Desktop on macOS and Windows silently ignores it. For those, add the bridge overlay:

docker compose -f docker-compose.yml -f docker-compose.bridge.yml --profile dashboard up -d

In bridge mode, set MREFD_IPV4_EXT/MREFD_IPV6_EXT so mDNS advertises the host's address rather than the container's. Add "ipv6": true to /etc/docker/daemon.json if you need IPv6. The overlay deliberately publishes UDP on IPv4 only, to work around a Docker Desktop dual-stack UDP bug. It does not publish UDP 5353, so mDNS from inside the container cannot reach the LAN in this mode. See Standalone advertiser for the workaround.

9mDNS discovery for local support networks

A field reflector does no good if the people next to it can't find it. Internet directories solve discovery for public reflectors. A shelter, an EOC, or a Field Day site may have no internet at all, or a link that is slow, metered, or saturated. mDNS covers that gap. Any reflector on the local network announces itself, and any M17 app on that network finds it within seconds. No one types an IP address, and no DNS server, internet link, or central directory is involved.

Why mDNS fits emergency and event networks

Zero infrastructure

mDNS needs only a shared network segment. A travel router, a Pi acting as an access point, or the venue's Wi-Fi is enough. It keeps working when upstream internet is lost.

Zero configuration for users

Volunteers arriving with phones or laptops join the site Wi-Fi, open the app, and the local reflector is already listed. There are no addresses to hand out and no typos to troubleshoot under pressure.

Addresses change; names don't

A field kit gets a different DHCP lease at every site. The announcement always carries the current address, so the app always connects to the right one.

Self-describing

The TXT record carries the callsign, modules, sponsor, name, and description. The app can show "Tulsa EOC Field Node – modules B, C, D" instead of a bare IP address.

mDNS is how the local support network (the club, the ARES group, or the served agency running the site LAN) tells every device on it that an M17 reflector is available here and how to reach it. The same mechanism lets that network point users at reflectors hosted elsewhere. See Support-network patterns.

How mDNS and DNS-SD work

Multicast DNS (RFC 6762) uses ordinary DNS messages, sent to a multicast group instead of a server: 224.0.0.251 for IPv4 and ff02::fb for IPv6, both on UDP port 5353. Each device answers for its own names in the .local. domain. These packets are link-local: routers do not forward them, so an advertisement reaches exactly the devices on the same network segment.

DNS-Based Service Discovery (RFC 6763) builds on mDNS. It defines a standard set of records so that clients can ask "which instances of service type X exist here?" and then "how do I reach this one?". M17 reflectors use the service type _m17._udp.

The records behind an _m17._udp advertisement

For a reflector M17-XYZ running on a host named fieldpi, the advertiser publishes four related records:

; 1. PTR — "an instance of _m17._udp exists, called m17-xyz"
_m17._udp.local.                 PTR   m17-xyz._m17._udp.local.

; 2. SRV — "that instance is served by host fieldpi, port 17000"
m17-xyz._m17._udp.local.         SRV   0 0 17000 fieldpi.local.

; 3. TXT — reflector metadata as key=value strings
m17-xyz._m17._udp.local.         TXT   "type=reflector" "designator=XYZ" "slug=m17-xyz"
                                       "name=Tulsa EOC Field Node" "sponsor=Tulsa ARC"
                                       "country=US" "url=https://m17.club.org"
                                       "ipv4=192.168.1.40" "port=17000" "modules=B,C,D"

; 4. A / AAAA — "fieldpi is at these addresses"
fieldpi.local.                   A     192.168.1.40
fieldpi.local.                   AAAA  2001:db8:10::40

The instance name defaults to the lowercase callsign (the slug), e.g. m17-xyz. If the slug is empty it falls back to the designator, then to the name. You can override it with --instance-name. The SRV target is the system hostname with any trailing .local removed before the domain is added. This prevents the doubled fieldpi.local.local. target that macOS hostnames would otherwise produce. The A/AAAA set contains every non-loopback address on the advertising interfaces. IPv6 link-local (fe80::/10) addresses are left out because they are unusable without a zone ID.

Long values. A single TXT string may hold at most 255 bytes. When key=value is longer than that, the advertiser splits the value across numbered keys (description0=, description1=, …). Clients rebuild the value by concatenating the numbered keys in order.

The advertiser inside the container

The image includes /usr/local/bin/m17-advertise, a static Go binary built from tools/m17-advertise with the libp2p/zeroconf library. On startup, entrypoint.sh does the following:

  1. Starts mrefd.
  2. Waits 10 seconds, so the reflector is already bound and accepting connections before any app is told about it.
  3. Derives designator and slug from MREFD_CALLSIGN, and converts MREFD_MODULES/MREFD_ENCRYPTION_ALLOWED into the advertiser's comma-separated form.
  4. If MREFD_ADVERTISE_CONFIG (default /etc/mrefd/site.json) exists, loads it as the base record. Values from environment variables are then overlaid on top.
  5. Runs m17-advertise. When it receives SIGTERM it sends goodbye packets (TTL 0), so apps drop the entry immediately rather than waiting for it to expire.

The advertiser is best-effort. If it exits, mrefd keeps running. If mrefd exits, the container stops the advertiser and exits too, so a stopped reflector is never left advertised.

Patterns for local support networks

Pattern 1: Field node on the site LAN

This is the standard case. The go-kit Pi runs the container with host networking on the same Wi-Fi or Ethernet that volunteers join. The reflector announces itself, apps list it, and users connect locally. If the uplink is up, the field node relays through its hub. If not, the site still has a working local net.

Pattern 2: Pointing a club or EOC network at a remote reflector

The club's hub may live on a VPS, not on the local network. A support network can still make it one-tap discoverable: run m17-advertise on any always-on LAN device (the router, a NAS, a Pi) with the hub's public address in the TXT record:

m17-advertise --designator HUB --slug m17-hub --name "Club Hub (internet)" \
    --dns m17.club.org --ipv4 203.0.113.17 --ip-source dns \
    --port 17000 --modules A,B,C,D --url https://m17.club.org
How clients pick an address

The SRV and A/AAAA records always describe the advertising host. The TXT ipv4, ipv6, and dns keys describe the reflector. When those differ, as in this pattern, the client must use the TXT values. Before relying on this pattern, confirm that your app honors them.

Pattern 3: Several reflectors at one site

A large event may run separate reflectors per function (operations, logistics, a shelter net), or keep a local field node beside a remote hub entry. Each has a unique instance name and appears separately in the app's list. Use MREFD_ADVERTISE_NAME and MREFD_ADVERTISE_DESCRIPTION to tell them apart at a glance.

Pattern 4: Isolated mesh with no uplink

On an AREDN or similar mesh, or an air-gapped incident LAN, mDNS still works within each broadcast domain. To reach across segments, see the gateway notes below.

Testing discovery

Run these from another machine on the same network:

# macOS
dns-sd -B _m17._udp                       # browse: list instances
dns-sd -L m17-xyz _m17._udp               # resolve: host, port, TXT
dns-sd -G v4v6 fieldpi.local              # addresses

# Linux (apt install avahi-utils)
avahi-browse -rt _m17._udp                # browse + resolve + TXT, then exit

# Raw packets, to see whether multicast arrives at all
sudo tcpdump -i any -n udp port 5353

If tcpdump on the client shows no packets from the reflector's address, the problem is the network (isolation, VLANs, firewall), not the software.

For application developers

Here is how to add LAN discovery to an M17 client:

  1. Browse for _m17._udp in domain local., using the platform API: NWBrowser/NetServiceBrowser on Apple platforms, NsdManager on Android, Avahi D-Bus or a library such as zeroconf elsewhere.
  2. For each instance, resolve SRV and TXT. Treat type=reflector as a reflector entry, and ignore unknown type values.
  3. Parse TXT into a dictionary. Merge numbered keys (description0, description1, …) back into their base key. Split modules and encrypted on commas into module letters.
  4. Pick the connect address in this order: TXT ipv6/ipv4 when present and reachable, then the resolved SRV target's addresses. Use port from SRV, falling back to TXT and then 17000.
  5. Show discovered reflectors in a "Nearby" section, separate from the internet directory, and remove them when the browser reports the service gone.
  6. Deduplicate against the internet directory by designator/slug, but prefer the LAN address while it is on the local network.

Security considerations

  • mDNS is unauthenticated. Any device on the LAN can advertise _m17._udp under any name. Treat discovered entries as convenient hints, not as trusted identity. At an incident, control who gets on the network.
  • Everything in TXT is broadcast to the whole segment. Don't put secrets, private contact details, or internal notes there.
  • mDNS is link-local by design and never leaves the segment unless you deliberately configure a gateway. Never port-forward UDP 5353 from the internet.
  • The relay link between field node and hub is separate from discovery. It is authenticated with TLS (see below).

10Interlinking and relay

Interlinks are declared in config/mrefd.interlink. Both sides must list each other, and edits take effect within seconds. One file can mix every form below.

UDP interlink (community standard)

# Static: literal IP and port
M17-URF   45.32.11.22  17000  B,C,D
# Pre-1.0 "legacy L" peer
M17-QQQL  44.45.45.100 A,B,C

Use UDP between fixed public reflectors, for example a hub peering with other dvref-listed reflectors or a URFD gateway. It needs no certificates. Upstream mrefd accepts only literal IP addresses or DHT lookups in this file, not hostnames, so it cannot follow a field node whose address keeps changing. That gap is what the TLS relay fills.

TLS relay: field node to hub

The fork adds a TLS-over-TCP interlink, always compiled in. The field node dials out to the hub on TCP, on the same port number as M17 UDP (17000 by default). It presents its operator's Ed25519 certificate and, after the TLS handshake, sends a signed BIRTH message (timestamp and nonce) naming the one module it is linking. The key decides who the node is. The hub looks the certificate up by its fingerprint (SPKI SHA-256), takes the callsign from the matching registration, and checks that the module is one that key may use. It then verifies the BIRTH signature and timestamp and installs the node as CALLSIGN-MODULE, for example W5ABC-B. After that, M17 voice and data frames flow inside the TLS session.

This works the way a radio connects to a reflector. An operator has one key, named with their bare callsign and shared by all their nodes, and each node says which module it links. W5ABC-B and W5ABC-C are two nodes holding the W5ABC key. The hub registers that key once, with the modules its nodes may use. The hub has one key of its own, named with its reflector callsign.

  • The field node's IP can change at every site. Neither side declares it ahead of time. If a node reconnects from a new address, the newest connection wins.
  • The field node needs no inbound port, so it works behind CGNAT, LTE, and Starlink.
  • Field nodes are never published anywhere; only their hub knows them.
  • The field node trusts the hub by pinning the hub's certificate file. Certificates are self-signed; no CA is involved.
  • The node keeps the link up by itself. Each reconnect is a fresh BIRTH. A link that dies silently is detected by TCP keepalive (about 5 minutes by default, see MREFD_TLS_KEEPALIVE).
  • Clocks on both ends must agree within MREFD_TLS_TIMESTAMP_SKEW (300 s). Use NTP, or GPS time when offline.

The protocol as built (message types, reject codes, threat model) is in docs/tls-interlink-design.md. For deciding whether a peering needs TLS at all, see deploy/INTERLINK-CHOICES.md.

Files and interlink lines

The host's config/tls/ is mounted read-only at /etc/mrefd/tls, by both the root docker-compose.yml and deploy/docker-compose.yml. The scripts write everything there:

FileOnWhat it is
config/tls/server.crt, server.keyHubThe hub's key, named with its reflector callsign (M17-HUB).
config/tls/peers/<CALL>.pub.pemHubOne registered certificate per field operator.
config/tls/client.crt, client.keyFieldThe operator's key, named with their bare callsign (W5ABC). The same pair goes on every node they run.
config/tls/hubs/<M17-XXX>.crtFieldPinned certificate for each hub this node links to.

The scripts also write the matching lines in config/mrefd.interlink. Modules may be written B,C, BC or "b c".

# Hub: one line per operator
W5ABC    B,C  key:/etc/mrefd/tls/peers/W5ABC.pub.pem

# Field node: one line per hub, exactly one module
M17-HUB  B    tls:hub.example.org:17000  servercert:/etc/mrefd/tls/hubs/M17-HUB.crt

The hub reloads its lines within seconds, with no restart. Adding the first key starts the TLS listener. Changing a key's modules disconnects that operator's nodes on the removed modules. Removing a key disconnects all of its nodes immediately. A field node's tls: lines take effect when the node restarts. Use a DNS name for the hub, not an IPv6 literal.

TLS setup, step by step

The example uses hub M17-HUB at hub.example.org and field operator W5ABC, whose nodes may use modules B and C. Run the scripts from the directory that holds config/ (the repository root, or deploy/). Every script takes --config <dir> (default ./config), accepts lowercase callsigns and modules, and prints --help.

  1. Hub, once: make the hub key. 
    scripts/tls-genkey.sh --role hub --identity M17-HUB
    It prints the key's fingerprint. Give config/tls/server.crt and the fingerprint to your field operators. Open TCP 17000 inbound on the hub's firewall, as well as UDP 17000 as usual.
  2. Field operator, once, on any machine: make your key. 
    scripts/tls-genkey.sh --identity W5ABC
    Send config/tls/client.crt (never the .key) to the hub operator, with the modules your nodes will use. Copy config/tls/ to each node you run.
  3. Hub, for each field operator: register their key. 
    scripts/tls-add-peer.sh --cert W5ABC.crt --modules B,C
    W5ABC.crt is the client.crt the operator sent, under any file name; the callsign is read from it. This takes effect live, with no restart. Any node holding the W5ABC key may now link module B or C.
  4. Each field node: link to the hub. 
    scripts/tls-add-hub.sh --hub M17-HUB --host hub.example.org --module B --cert M17-HUB.crt
make restart        # or: docker compose restart mrefd
    M17-HUB.crt is the hub's server.crt, under any file name. A second node is the same with --module C. The hub sees them as W5ABC-B and W5ABC-C.
  5. Check it. The log (make logs or docker compose logs -f) shows link UP on both ends, and the dashboard's TLS Links page lists the link. On either end: 
    scripts/tls-list-peers.sh
scripts/tls-verify.sh --host hub.example.org --expect-fingerprint <FP>   # from a field node: is the hub reachable, and is it the right hub?

Changes later

  • Revoke an operator: scripts/tls-remove-peer.sh --identity W5ABC on the hub. Live: their nodes are disconnected at once.
  • Change an operator's modules: run tls-add-peer.sh again with the new --modules. Live: nodes on removed modules are disconnected.
  • Rotate the hub key: scripts/tls-rotate-server-cert.sh --identity M17-HUB, restart the hub, and have every field operator rerun tls-add-hub.sh with the new certificate and restart their nodes.
  • Remove a hub link from a field node: scripts/tls-add-hub.sh --hub M17-HUB --remove, then restart the node.

Running the scripts

The scripts need OpenSSL 1.1.1 or newer for Ed25519. On macOS, the built-in /usr/bin/openssl is LibreSSL and can't do it; the scripts find Homebrew's openssl@3 automatically if it is installed (brew install openssl@3). Linux needs nothing extra.

Without a usable openssl, run the same scripts from the image. They are installed there as tls-genkey, tls-add-peer, tls-add-hub, tls-remove-peer, tls-list-peers, tls-rotate-server-cert and tls-verify, and default to --config /etc/mrefd:

docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/config:/etc/mrefd" \
    --entrypoint tls-genkey ghcr.io/greggwon/mrefd:latest --identity W5ABC

Key and certificate details, including making them with plain openssl, are in deploy/CERTS.md.

Watching links

Log lines. Each end logs link UP when a link comes up, and link DOWN when it drops:

TLS interlinks: link UP: to 'M17-HUB' at 203.0.113.17:17000 as 'W5ABC-B' (module B)
TLS interlinks: link DOWN: to 'M17-HUB' at 203.0.113.17:17000 after 2h14m: no response from peer (TCP keepalive/retransmit timed out; link or peer is down) (frames in 18234, out 17990, stale voice dropped 0); reconnecting

The reason is in plain English: no response (keepalive timed out), connection reset by peer, peer sent DISCONNECT, DNS lookup failed, connection refused, or hub rejected us: … with the cause (key not registered, module not allowed, clocks differ). Connection attempts are logged for the first three tries and then every tenth, with how long the link has been down. Two more messages report a slow link: is falling behind (once per transmission, when voice delay is growing) and can't keep up with voice: dropped N stale voice frame(s) (every 10 s while voice is being dropped). See Slow links.

Dashboard. The TLS Links (up/total) page lists each link with its state (connected, connecting, retrying, disconnected), last error, frame counts and voice queue figures. A TLS badge appears on every page:

BadgeMeaning
GreenLink up. A steady voice delay is still green.
YellowVoice falling behind: the delay is growing.
RedVoice can't keep up (stale voice is being dropped; use data), or the link is down.
GreyWaiting for nodes to connect.

The same figures are in the TLS object of mrefd.json (Listening, Registrations, and Links[] with State, LastError, FramesIn/FramesOut, VoiceDropped, VoiceDroppedRecent, VoiceQueue, VoiceQueuePeak, VoiceLateMs, VoiceTrend).

From a shell: scripts/tls-list-peers.sh shows the registered keys or hub links and their live state (--json for machine output).

Slow links: voice vs data

Voice over the TLS link needs about 31 kbit/s each way. Each 61-byte M17 frame becomes about 150 bytes with TLS, TCP and IP overhead.

mrefd keeps voice current. Voice that has waited in the send queue longer than MREFD_TLS_MAX_AUDIO_MS (200 ms) is dropped, not sent late. Network latency alone never causes drops: a link with a long but steady delay is fine. Only a link slower than the voice makes the queue grow. Data (packet mode, M17P) is never dropped for age; it is capped at MREFD_TLS_DATA_QUEUE_KB. Control messages go first, then voice, then data.

There is no connect timeout. TCP retries run their full course, so slow or lossy links still connect.

Simulated linkVoice delivered

If audio breaks up, the log reports dropped voice frames, or the badge turns yellow or red, switch to data (packet mode) on that link until it improves.

Rules for derived images
  • Keep the entrypoint. It renders mrefd.cfg, starts mrefd, and starts the advertiser. To change its behavior, COPY a modified script over /entrypoint.sh rather than replacing ENTRYPOINT.
  • Always end with USER mrefd, and use --chown=mrefd:mrefd on files you add under /etc/mrefd.
  • Never bake private keys (server.key, client.key) into an image you push. Mount config/tls/ at run time.
  • Values that differ per node stay out of the image. Callsign and email go in mrefd.env; the image holds only what every node of that kind shares.

Keeping it current: a derived image is a snapshot of its base. To pick up a new release, run docker build --pull -t my-mrefd:field . and then docker compose up -d. For repeatable builds, pin the base by digest: FROM ghcr.io/greggwon/mrefd@sha256:<digest>.

git merge upstream/master          # into the fork branch you deploy
cd ..
git add mrefd && git commit -m "bump mrefd"
make build-local && make restart

If a new upstream release adds settings to example.cfg, add them to .env.example and to docker/mrefd/entrypoint.sh.

Field kit checklist

  • Pi with SD card or SSD, a reliable power supply, and an image already pulled (docker compose pull before you leave home).
  • Your own travel router or access point, with client isolation off, so mDNS works regardless of the venue.
  • config/tls/client.crt/client.key and config/tls/hubs/<hub>.crt installed, and the tls: line written by tls-add-hub.sh.
  • A time source: NTP when online, GPS when not. The hub rejects a node whose clock is more than 300 s off.
  • Test once on the home network: the app finds the node over mDNS, the log shows link UP, and the TLS badge is green.

13Troubleshooting

SymptomCause and fix
MREFD_CALLSIGN is required / must be 'M17-' followed by 3….env is missing or still has placeholders. Run make init or edit the env file.
Is a directory on a list fileDocker created a directory where a bind-mounted file was missing. Stop the container, rmdir it, touch the file, and start again.
App on the same Wi-Fi doesn't list the reflectorCheck, in order: MREFD_ADVERTISE_ENABLED, host networking, the log line starting Bonjour advertiser, client isolation, VLANs, and the host firewall on UDP 5353. Run avahi-browse / dns-sd from another machine.
Listed, but the connection failsThe advertised address is unreachable (multi-homed host, or a stale MREFD_IPV4_EXT). Pin --iface or correct the TXT address. Also check that UDP 17000 is open on the LAN.
SRV target shows host.local.local.Old advertiser build. Rebuild the image.
Nothing discovered on Docker Desktop (Mac/Windows)Expected. Set MREFD_ADVERTISE_ENABLED=false and run m17-advertise natively on the host.
"Connection refused" on UDP from macOSDocker Desktop dual-stack UDP bug. Use docker-compose.bridge.yml, which publishes UDP on IPv4 only.
Peers connect but no audio passesThe two sides have different encryption settings on a shared module.
Field log: hub rejected us: our key isn't registered there
Hub log: TLS server: unregistered key (CN '…', fingerprint …)		The hub has no registration for this operator's key, or has an old copy after the operator made a new key. On the hub: scripts/tls-add-peer.sh --cert W5ABC.crt --modules B,C (add --force to replace an old key).
Field log: hub rejected us: module B isn't allowed for our key at the hub
Hub log: 'W5ABC-B' asserted module(s) 'B'; key 'W5ABC' may assert one of 'C'		The node links a module the hub hasn't allowed for this key. Rerun tls-add-peer.sh on the hub with the module added, or change the node's module with tls-add-hub.sh and restart it.
Field log: hub rejected us: our clock and the hub's differ too much (check NTP on both ends)
Hub log: BIRTH verify failed		The clocks differ by more than MREFD_TLS_TIMESTAMP_SKEW (300 s). Fix NTP (or GPS time) on both ends.
Container exits: MREFD_TLS_CLIENT_KEY=… isn't readable by mrefd (uid 1000). On the host: sudo chown 1000 config/tls/*.keyThe key was made by a different user and is mode 0600. Run the printed command on the host, then start again.
Log: can't keep up with voice: dropped N stale voice frame(s) in the last 10s, or is falling behind; badge yellow or redThe link is slower than voice needs (about 31 kbit/s each way). Use data (packet mode) on that link until it improves. See Slow links.
Field log: TLS handshake failed: the hub's certificate doesn't match our servercert: pinThe hub key was rotated, or the wrong certificate was pinned. Get the current server.crt from the hub operator, rerun tls-add-hub.sh, restart. tls-verify.sh --host … --expect-fingerprint … confirms which hub answers.
Field log: connection refused, is the hub's TLS listener running?Open TCP 17000 inbound on the hub. The hub starts listening only once at least one operator key is registered.
Hub log: registers operator keys, but MREFD_TLS_SERVER_CERT / MREFD_TLS_SERVER_KEY aren't setThere is no config/tls/server.crt/server.key. Run tls-genkey.sh --role hub --identity M17-HUB and restart.
Hub log: belongs to 'X', but the interlink line says 'Y'; skippingA hand-edited key: line names a different callsign than its certificate. Remove the line and register with tls-add-peer.sh.
Node log: must assert exactly one moduleA field node's tls: line has more than one module letter. Each node links exactly one module per hub.
linux/arm/v7 build fails with shift-count-overflowThe submodule predates the users.cpp fix and the Dockerfile sed didn't match. Move the submodule to a newer commit.
